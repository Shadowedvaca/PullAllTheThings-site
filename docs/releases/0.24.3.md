# Pull All The Things 0.24.3

## Highlights

- Prepares an owner-selected release candidate with canonical delivery, testing,
  coverage, browser-validation, runtime-identity, and promotion controls.

## Fixes/Changes

- Uses root `VERSION` as the application version authority and reports version,
  environment, and commit identity through FastAPI and `/api/health`.
- Adds curated release records, validation, exact-SHA deployment evidence, and
  post-production GitHub Release publication.
- Defines repository-owned static, unit, integration, regression, migration,
  provider-boundary, coverage, automated UI/E2E, and deployed-smoke expectations.
- Establishes measured fail-closed floors of 37% overall statement coverage and
  72% changed-line coverage, with an owner-approved exception process for any
  decrease.
- Adds a Chromium journey for the public login-to-registration path and retains
  coverage and browser failure artifacts in pull-request validation.
- Requires automated regression protection for defect fixes and distinguishes
  automated browser evidence from Parent-timed human UI validation.
- Removes the documented hotfix path that permitted production promotion before
  exact-SHA Test evidence completed.
- Keeps Production repository-blocked pending the migration/recovery and
  GitHub/SSH/credential controls owned by issues #54 and #55.
- Replaces stateless 30-day authentication with approved database-backed,
  independently revocable sessions: 7 days for ordinary members and 12 hours
  for rank level 4 and above, with no automatic renewal.
- Revalidates active-user and current-rank state on every authenticated request,
  revokes sessions on security-sensitive account or privilege changes, uses POST
  logout, and rejects cross-origin unsafe cookie-authenticated requests.
- Adds fail-closed, environment-specific pre-deployment PostgreSQL custom-format
  backups with archive inspection, checksums, migration identity, and non-secret
  rollback manifests before the migration-running container can start.
- Adds isolated CI archive restore/fingerprint and representative
  downgrade/re-upgrade rehearsal, plus a production-image boot against a fresh
  ephemeral PostgreSQL 16 database with exact runtime and migration identity.
- Replaces the mutable third-party SSH deployment action with native OpenSSH,
  strict supplied known-host verification, and environment-scoped host, user,
  and key contracts. Adds a machine-validated GitHub protection manifest without
  adding another routine reviewer approval.
- Makes Development deployment and exact runtime-identity verification mandatory
  preparation before any Child- or Parent-timed manual UI checklist is handed to
  a person, with a repository regression contract preventing stale-environment
  validation handoffs.
- Pins each environment-specific Compose app service to its correct runtime
  identity, preventing host environment files from making Test identify as
  Production.
- Removes deployment-host GitHub fetches. Each workflow creates and verifies an
  immutable Git bundle from its exact checked-out commit, transfers it using
  strict environment-scoped SSH trust, imports it locally, verifies and checks
  out the exact SHA, and removes the temporary bundle on success or failure.
- Makes remote deployment fail closed by replacing SSH-stdin-streamed deployment
  source with a checked-in program, detaching Docker and backup stdin, and
  requiring an exact post-backup/post-health/post-migration completion sentinel.
- Distinguishes a temporary Production attempt tag from a successfully deployed
  or released immutable tag. A failed unpublished attempt can be retired only
  manually after exact-object/run/Release validation; retry still requires the
  corrected PR, exact-SHA Test evidence, and a new Production approval.
- Requires every historical Production run ID and commit SHA to be declared
  when validating a reused failed-attempt tag, preventing either an older
  attempt or a newly observed run from being omitted from retirement evidence.
- Bundles and declares a repository-owned favicon for public, authenticated, and
  setup pages, and serves the conventional `/favicon.ico` request without the
  browser-console 404 found during Development validation.

## Deployment/Migrations

- Migration 0182 creates `common.auth_sessions` plus password, account-state,
  and rank-change revocation triggers. Existing stateless tokens do not have a
  persisted session identifier and become invalid after deployment; users must
  sign in again. Deployment workflows resolve and verify an exact commit.
- This is a release candidate record, not deployment evidence. Test and
  Production promotion remain separately gated.
- The first `prod-v0.24.3` attempt failed before deployment completion and
  Release publication. Its preserved evidence does not consume Mike's selected
  version; issue #69 governs manual retirement and any later recreation on the
  corrected exact Test-proven commit.
- Deployment workflows now stop before container startup when the atomic
  pre-deployment archive, inspection, checksum, Alembic identity, or rollback
  manifest cannot be produced.
- Deployment success now requires the checked-in remote program to verify exact
  runtime identity, connected database, current migration head, and the atomic
  active-SHA marker before emitting the completion sentinel accepted by CI.

## Rollback

- Before merge, revert the focused child commits from draft PR #56. After an
  authorized compatible release, use the recorded previous and target commits,
  backup checksum, and migration identity to choose a compatible code/database
  pair. Redeploy a prior successfully deployed immutable tag only when database
  compatibility is established. Never move, delete, or reuse a successfully
  deployed or released tag, and never automatically downgrade/restore a live
  database; destructive recovery requires exact authority under the backup
  runbook. Failed unpublished attempt retirement is a separate release-lifecycle
  operation, not rollback.

## Known Limitations

- Production readiness is enabled, but the failed attempt is not a release.
  The current failed tag must be retired after complete multi-attempt evidence;
  the eventual corrected tag must target a successful exact-SHA Test commit and
  still requires a separate Promotion to production approval before any retry.
- Local child #59 coverage could not execute PostgreSQL-dependent tests or the
  container gates; hosted PR CI remains the required authority for those layers.
